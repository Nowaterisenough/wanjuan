# 对象同步的增量读取与可观测性

## 原有瓶颈

上传端已有待同步队列，不是每次整库上传。主要冗余位于拉取和调度：

- GitHub 目录结果丢弃 SHA，修改时间又恒为零，导致每轮读取全部对象正文。
- 书籍按组件合并、删除记录按版本竞争，需要同时核验活对象和墓碑；旧拉取链路没有可靠内容缓存。
- WebDAV 重复枚举相同目录，初始化预先检查不使用的目录，请求串行放大网络往返。
- 检查单本书是否存在时重新读取全部书籍，产生近似平方级的本地记录读取量。
- 本地修改也触发完整拉取；相同请求加入正在进行的同步时还会要求尾随整轮重跑。
- 本地变更捕获及书架变更指纹每次重新读取全部书源规则。
- 界面只有阶段文案，看不到已检查对象、传输对象和缓存复用数量。

## 新流程

1. 按表失效记录本地变更类型。首次运行和切换服务器全面对齐，后续只重算失效类型。捕获使用代数，捕获期间的新写入不会被误清除。
2. 本地自动触发合并后仅推送待同步项。启动、联网、下拉和手动同步保留双向检查，重叠请求共享执行。
3. GitHub 通过一次递归仓库树请求获取对象 SHA；WebDAV 按唯一目录、有限并发获取 ETag。GitHub 索引截断或目录请求失败不能推进为成功。
4. 按服务器、对象路径及版本读取缓存。只对缺失或版本不同的对象请求正文，最多并发四个请求，每批最多保留 32 项正文。
5. 书籍的活对象与墓碑仍一起比较版本；缓存只替代网络读取，不跳过冲突处理、本地存在性检查或恢复丢失本地书籍。
6. 并发写入继续读取服务器最新对象并使用 SHA/条件写入重试，绝不使用拉取缓存代替冲突读取。只有写入正文与服务器回执版本匹配时，才预热该版本缓存。
7. 顺序应用变更，成功后确认本地队列；目录更新结束只补捕获书籍类变更，不重新扫描书源规则。

## 边界与兼容性

- 保留原有 `sync/v1/` 对象结构，不需要迁移云端格式，旧客户端写入产生新 ETag/SHA 后仍可识别。
- 传输粒度是变化的对象，不是数据库整包，也不是任意字段的文本补丁；书籍内部仍按书架、目录和进度组件合并。
- 没有可靠版本标识的 WebDAV 必须保守读取，不能用相同秒级修改时间或文件大小推断内容相同。
- 初次建立基线、清理缓存、缓存损坏、更换服务器会增加正文读取，这是安全恢复路径而非永久关闭增量。
- GitHub 树索引若被截断则中止，不将缺失条目推断为删除；删除始终由显式墓碑表示。普通 WebDAV 可能短暂漏列，遇到缺少活对象的墓碑时，会定点读取活对象确认，避免旧墓碑删除漏列的新版本。
- 进度统计的是处理对象数；索引、条件写入、合并及重试会产生额外 HTTP 请求。

## 验证口径

以固定远端集合比较相邻两轮正文 GET，而非只测页面动画：首次建立 500 项基线；无变化应为零次正文 GET；仅一项版本变化应为一次正文 GET。另测同秒修改、缓存丢失、服务器隔离、活对象/墓碑竞争、写入回执、捕获期间写入和无版本回退。

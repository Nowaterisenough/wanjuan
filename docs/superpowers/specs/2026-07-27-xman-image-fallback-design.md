# 禁漫漫画图片候选节点回退设计

## 背景与结论

禁漫正文中部分图片长期停留在 `1%`，并不是已经下载了 1%，而是 `ProgressManager` 在注册监听器时硬编码的初始显示。实际请求通常还没有收到图片数据。

对同一批 nnpic 图片在 App 外直接访问的结果表明，问题可在浏览器或命令行中复现：`img.nnpic.xyz` 会间歇性出现较长首字节等待和 HTTP 520，而相同路径切换到其他分片后可以快速成功。因此根因是 CDN 节点间歇性不稳定；App 的问题是绕过了网页自带的候选节点回退逻辑，只会反复请求单一节点。

本次实现一个由书源按需启用的通用漫画图片候选地址机制。Kotlin 网络层不识别或硬编码禁漫、nnpic、p8 等业务域名；禁漫书源只负责生成候选地址，通用加载器负责执行回退。

## 目标

- 主节点发生 HTTP 错误、无数据超时或传输失败时自动尝试候选节点。
- 单节点连续 8 秒没有收到新数据时切换，但不限制持续传输图片的总下载时间。
- 初始和节点切换阶段显示“连接中”，收到数据后显示真实进度。
- 候选请求继承原请求的 Header、Cookie 和书源图片解密行为。
- 无论哪个候选成功，都使用原始 Glide 模型键缓存。
- 未配置候选地址的其他书源保持原有行为。
- `last.nnpic.xyz` 保持原地址，不加入候选回退。

## 非目标

- 不修改网页站点或其 JavaScript `ComicLoader`。
- 不在 Kotlin 层维护禁漫 CDN 节点名单。
- 不把所有 nnpic 地址无条件改为 p8。
- 不改变普通封面、RSS 图片和未启用候选功能的漫画图片行为。
- 不为 Glide 最终像素解码失败增加跨层重试协议。

## 书源 URL 选项

在现有 URL 选项中增加两个可选字段：

```json
{
  "fallbackUrls": [
    "https://img.example/image.jpg",
    "https://p4.example/image.jpg"
  ],
  "fallbackTimeout": 8000
}
```

- `fallbackUrls` 是已经由书源计算完成的候选 URL 数组。
- `fallbackTimeout` 的单位是毫秒，禁漫设置为 `8000`。
- `fallbackUrls` 非空但超时缺失、不是正数或无法解析时，使用默认值 `8000`。
- 主 URL 始终排在候选数组之前。
- 空地址、无效地址、与主地址重复的地址及重复候选会被过滤。
- 没有 `fallbackUrls` 时忽略 `fallbackTimeout`，沿用当前单地址加载流程。

`AnalyzeUrl.UrlOption` 负责解析字段，并向图片请求层提供主地址、候选地址、超时和已经解析好的 Header。候选地址不得再次执行整条书源 URL 脚本，以免产生副作用或得到不同的认证状态。

## 禁漫候选地址规则

禁漫正文规则先把懒加载属性转换为绝对地址，再根据主机名生成 URL 选项：

- `img.nnpic.xyz` 和 `p数字.nnpic.xyz`：主地址使用 `p8.nnpic.xyz`。
- 原始主机优先作为第一个候选，其后按网页现有节点集合补充 `img、p4、p6、p9、p10、p11`。
- 主地址、原始地址和补充候选统一去重。
- 所有地址保持原路径、查询参数和片段不变。
- `last.nnpic.xyz`、其他 nnpic 主机和非 nnpic 地址原样返回，不附加 URL 选项。

示例：

```text
输入：https://p9.nnpic.xyz/upload_s/a.jpg?token=1
主地址：https://p8.nnpic.xyz/upload_s/a.jpg?token=1
候选：p9 → img → p4 → p6 → p10 → p11
```

## 加载架构与数据流

1. 漫画正文将包含 URL 选项的原始图片字符串交给 Glide，原始字符串继续作为模型和缓存键。
2. `OkHttpStreamFetcher` 使用 `AnalyzeUrl` 得到主地址、候选数组、超时、Header 和 Cookie 配置。
3. 未配置候选时执行现有请求路径；配置候选时依次请求“主地址 → 候选地址”。
4. 每个候选创建独立请求，并继承相同的 Header、Cookie、限速器和漫画进度能力。
5. 回退模式下，响应数据先写入临时文件。只有完整接收成功并完成现有书源图片解密后，才把可读取的数据交给 Glide。
6. Glide 使用原始模型完成解码和缓存，实际成功节点不会成为新的缓存键。
7. Glide 清理 DataFetcher 时关闭流并删除临时文件。

临时文件只用于配置了候选地址的请求，避免为了发现中途断流而把完整大图保存在内存。已有 `imageDecode` 规则需要字节数组时仍沿用现有解密接口，并在解密失败时尝试下一候选。

## 超时与失败判定

`fallbackTimeout` 是每次读取的无数据超时，不是整个请求的总时长。只要服务端持续提供数据，下载可以超过 8 秒。

以下情况会关闭当前响应、清理当前临时数据并尝试下一候选：

- DNS、TLS、连接或其他 `IOException`。
- HTTP 状态不是 2xx。
- 连续超过 `fallbackTimeout` 没有收到数据。
- 响应体为空或未完整传输。
- 现有书源 `imageDecode` 返回空值或抛出异常。

所有候选都失败后，只向 Glide 回调一次失败，并在异常中保留各候选的失败原因。日志记录候选主机、状态码或异常类型，不记录查询参数、Cookie 或其他敏感数据。

网络层无法获知 Glide 在 `onDataReady` 之后的最终像素解码结果，因此这类失败不在同一次 DataFetcher 生命周期内切换候选。它仍进入现有重试界面；再次重试会重新执行完整候选链。已复现的 1% 问题发生在首字节到达前或 HTTP 520 阶段，不依赖该能力。

## 取消与并发

- `cancel()` 设置取消状态、取消当前 OkHttp Call，并终止等待中的协程或文件复制。
- 取消后不得启动下一候选，也不得调用成功或失败回调。
- 每次尝试开始前和回调前都检查取消状态，避免取消与网络回调竞争。
- 每个 DataFetcher 只维护自己的候选索引、Call、流和临时文件，不共享可变重试状态。
- 现有漫画请求限速器继续作用于每个实际网络请求。

## 进度显示

进度监听器使用原始图片 URL 作为稳定键，而不是当前候选请求 URL。

- 注册监听器时发送连接状态，`MangaVH` 显示“连接中”，不再显示硬编码的 `1%`。
- 每次开始新候选时重新发送连接状态。
- 收到首批数据后，已知总长度时显示实际百分比；未知总长度时显示通用加载状态。
- 成功、最终失败、取消或 ViewHolder 回收时移除监听器。
- 候选请求通过请求标签携带原始进度键，使拦截器能够把 p8、p9 等实际请求统一映射回原始图片。

## 缓存行为

- Glide 的 source key 继续使用传入加载器的原始模型。
- 候选地址只存在于 `AnalyzeUrl` 和 DataFetcher 内部，不作为新的 Glide model 发起加载。
- 失败候选的响应和临时文件不进入 Glide 缓存。
- 成功候选交给 Glide 后，仍按现有 `DiskCacheStrategy.ALL` 缓存。
- 手动重试先经过缓存；确需网络加载时重新执行完整候选链。

## 自动化测试

### URL 选项与兼容性

- 解析 `fallbackUrls` 和 `fallbackTimeout`。
- 过滤空值、无效 URL 和重复地址。
- 未配置候选时的请求行为与现状一致。
- 候选继承 Header 和 Cookie 配置，路径与查询参数不丢失。

### 候选请求状态机

使用可控的测试服务器或请求替身覆盖：

- 主节点 520，第二节点成功。
- 主节点无数据超时，第二节点成功。
- 主节点中途断流，第二节点成功。
- 空响应和书源解密失败触发回退。
- 全部失败时只回调一次失败。
- 取消后不再请求候选，也不产生迟到回调。
- 成功、失败和取消路径均清理响应、流和临时文件。

### 进度与缓存

- 初始状态和节点切换显示“连接中”。
- 候选进度映射到原始 URL，多个并发图片不会串进度。
- 收到数据后显示真实百分比。
- 成功结果的 Glide source key 保持为原始模型。

### 禁漫书源规则

- `img` 与所有 `p数字` 主机优先生成 p8 主地址。
- 原主机优先进入候选，其余节点按固定顺序补齐并去重。
- 路径、查询参数和片段保持不变。
- `last.nnpic.xyz` 和非目标域名不产生候选选项。
- 现有懒加载属性回退和相对地址补全测试继续通过。

## Release 验收

项目禁止以 Debug 构建代替验收。实施完成后：

1. 只运行 Release 单元测试和签名 Release 构建。
2. 按项目现有版本规则自增版本号。
3. 将新 Release APK 安装到模拟器并启动 App。
4. 重新导入修改后的禁漫书源，确保数据库不继续使用旧规则。
5. 加载目录并连续浏览多章正文，重点检查此前停留在 1% 的图片。
6. 确认等待首字节时显示“连接中”，收到数据后显示真实进度，节点失败时可自动恢复。
7. 结合不含敏感信息的日志确认候选切换确实发生。

若执行时没有可用模拟器，必须明确报告 Release APK 已完成的自动化验证和安装阻塞；不得构建 Debug 版本作为替代。

## 成功标准

- 自动化测试可以确定性证明 520、无数据超时和中途断流会切换候选。
- 禁漫实际阅读不再因单个 nnpic 节点异常而长期停留在 1%。
- 初始加载文案不再把“尚未收到数据”误报为 `1%`。
- `last.nnpic.xyz` 与其他未配置书源无行为回归。
- 签名 Release 构建成功、版本号自增，并在可用模拟器上完成安装、导入书源和启动验收。
